# 簽單網頁自動產生對帳單

本方案沿用既有簽單網頁與 Firestore，不需 NAS 或部署 Cloud Functions。

## 使用

1. 結帳日正常簽名。簽名雲端儲存成功並經讀回確認後，網頁會檢查該店是否到結帳日。
2. 任一方已有簽名即可產生本期對帳單，畫面顯示「正在產生」，完成後顯示「已放入送件中心」。不會實際傳 LINE。
3. 網路中斷或關閉頁面未完成時，重新開啟同一家店的簽單，或按「重試產生對帳單」。網頁會檢查最近到期的一期，並補做本機記住的失敗帳期；也可選擇要補做的結帳日。
4. 已有該店該帳期帳單會跳過。人工修改或再次簽名不會自動建立新版；需要更新仍從財務系統手動產生。

本版從 2026-10-30 起啟用，不會批次補產啟用前的舊帳期；歷史帳單請從財務系統手動產生。

## 區間與資料

25 號組：上月 26 日～當月 25 日；月底組：當月 1 日～最後一天。優先依 Firestore 已儲存的分組，否則用財務頁既有名單。鼎王依部門分帳。

採用簽名當下雲端已有的整期物流資料，沿用財務計價、春節加價、回饋、管理費與稅額。之後新增的明細不自動補入既有帳單。未簽名的結帳日資料不觸發。

補做只針對目前開啟的飯店，不會因為開一間店的簽單而批次產生全部飯店帳單。

## 防重與失敗處理

使用現有 statement_cases 的「客戶＋帳期」固定文件 ID，在 Firestore transaction 中先讀取再新增；已存在就不寫入。多裝置同時簽名與重開頁面都不會產生第二份自動帳單。

只有交易成功才顯示產單完成。產單失敗不回滾已儲存的簽名，也不顯示簽名失敗。未完成的帳期會先記住飯店和日期，重新開頁後重讀雲端資料再試；不把帳單假裝當成已成功寫入。

本方案不使用新集合權限，沿用 statement_cases 現有讀寫權限。若簽單頁顯示 permission-denied，代表目前部署的 Firestore rules 不允許該用戶端操作送件中心，需先檢查實際規則；不要將整個資料庫改成公開以排除錯誤。

帳單本身即為一次性保護，請勿刪除該期帳單。如果之後部署後端方案，它也會在發現既有帳單時跳過，兩邊不會互相覆蓋。

## 等待時間

需讀取價目、設定與當期明細，速度取決於手機網路與資料量。5～20 秒是預估，尚未量測現場實際耗時；較慢時可能超過。雲端讀取逾時會顯示重試提示。簽名儲存與對帳單產生有各自明確狀態。

## 維護與驗證

signature-statement-client.js 以延遲匯入接到 logistics.html，產單模組下載失敗不會阻止原有簽名程式啟動。

共用 firebase-signature/functions/lib 的純計價函式與結帳規則，沿用前次後端準備的相同版本。若日後財務計價或分組預設名單變更，需同步更新此共用模組。

本地檢查：簽單模組語法、已簽即產生整期、重新開頁補產、無簽名不產生、價目讀取失敗／交易失敗後重試、兩裝置併發去重、人工帳單優先，以及後端共用規則測試。未對正式簽單新增假簽名或測試帳單。

執行：

```bash
npm run test:signature-statements
```
