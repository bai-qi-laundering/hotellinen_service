# 布品系統健檢與修復 — 2026-10-05

檢查基準：`7ffca9ec01df48174e37eaba695d963ac1608ffa`。
檢查範圍：布品登記 `index.html`、後台 `boss_admin.html`、飯店簽收 `logistics.html`、財務 `finance.html`。

## 確認的問題與修復

| 問題 | 原因 | 修復 |
|---|---|---|
| 後台更改物流數量後，財務更新仍顯示舊值 | 財務同區間資料快取 10 分鐘，手動更新也共用快取；SDK 讀取可能使用離線資料 | 手動更新由伺服器重新讀取。伺服器失敗時顯示讀取失敗，不將舊值當作最新 |
| 後台再次載入仍看不到其他頁面修改 | 同一日期區間直接返回本地紀錄 | 保留既有篩選操作，手動載入改讀伺服器 |
| 財務改品項名稱後出現新、舊兩個品項 | 財務只修改名稱；後台依盤點舊名稱自動補缺，簽收也只依目前名稱配對 | 更名保留原始盤點名稱及名稱歷程。後台補缺、盤點搬日期、強制同步、簽收讀取辨識同一來源 |
| 財務修改錯列或覆蓋同時更新 | 以陣列位置辨識品項，讀取後整陣列覆寫 | 依原品項來源在交易中找到最新項目；保留其他項目及欄位；名稱衝突提示重新確認 |
| 只有盤點紀錄的物流列，手動改實收未能保存 | 後台顯示尚未建立的物流列，更新卻要求資料庫已存在 | 使用既有單據建立規則保存整張來源清單與本次修改，讓財務能讀取 |
| 再簽名或重新同步遺失財務名稱、單價等資料 | 簽收用少數欄位重建整份品項清單 | 與交易中的最新品項合併，保留財務欄位及未顯示的其他項目 |
| 簽收畫面覆蓋後台新實收量 | 簽收頁可能仍停在更新前的快照 | 儲存時比較載入數量與最新數量，有衝突要求重新載入；自己的已完成寫入可安全重試 |
| 舊日期格式與標準格式混用時漏單，跨月尤甚 | 財務只有標準日期完全查不到才查舊格式；未補零日期的字串大小順序不等於日期順序 | 同時以月份前綴讀取字串日期及既有 Timestamp 相容範圍，再標準化、精確過濾、依文件 ID 去重 |
| 不同使用者更新生效日價目可能互相覆蓋 | 先讀後寫整份規則，無交易保護 | 保留原本生效日規則與計算方式，只將合併改為交易 |

## 保留的功能與規則

- 沒有加入新的送洗對點功能、欄位或自動排程。
- `index.html` 未修改，原本現場登記、複點及簽名流程維持原樣。
- 財務仍以物流實收量請款，0 或未填寫不回填出貨量，回洗品項排除規則維持原樣。
- 手動日期、鎖單時間、司機名單、雙簽名規則、價目生效日、春節規則、回饋、管理費、稅金及四捨五入方式未調整。
- 簽收畫面現在也能顯示後台已建立、但盤點清單沒有的物流品項，避免再簽名時遺漏。

## 驗證與限制

執行 `node --test tests/audit-regressions.mjs`，16 項離線回歸測試通過；四份 HTML 的內嵌 JavaScript 與共用模組通過語法檢查。

測試使用隔離的資料快照與 Firestore 模擬，未連線、修改或刪除正式帳務紀錄。尚未用真實飯店帳號、正式 Firestore 權限及實際 iPhone 完成端到端操作，因此不能據此宣稱所有線上環節已驗證。瀏覽器執行環境沒有可用的 Chromium 執行檔，未完成瀏覽器自動化驗證。

GitHub 專案不包含 Apps Script 原始碼及 Firebase 權限規則；本次無法檢查其內部實作。試算表價目及客戶 API 的既有行為維持原樣。

原先已發生的不同名稱重複紀錄，沒有更名前的來源資訊時，不能可靠判斷是同品項改名還是兩種真實品項，因此沒有批量自動合併。新更名會保留來源，避免相同原因再次發生。
