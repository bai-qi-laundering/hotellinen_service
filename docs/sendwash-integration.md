# 送洗對點單整合

本次保留登記單既有的 count／doubleCount 數量欄位，沒有增加數量欄。只針對試算表設定的品項使用新流程，其他簽收、出貨、財務及價格功能不變。

## 必須完成的後端設定

已依使用者提供的現行 Apps Script 完成整合，完整程式在 `hotellinen-apps-script.gs`，包含原試算表 ID。現行 Firebase 規則尚未提供；Apps Script 部署亦尚未更新。

1. 備份原 Apps Script 程式碼，使用 `hotellinen-apps-script.gs` 完整內容取代原程式碼檔並儲存。此檔已包含讀取函式，請勿再重複貼上 `sendwash-settings.gs`，也不要新增第二個 doGet／doPost。執行 `baiqiSetupSendwashSettingsSheet` 建立空白「送洗對點設定」分頁；第一列如下：

   飯店｜部門｜品項｜預設數量｜單位｜排列順序｜是否啟用

   顯示順序直接依「送洗對點設定」分頁由上到下的列順序。「排列順序」欄為舊版相容欄，可留白，數字不再影響排序。調整列的位置後，在登記頁按「更新設定」，再重新整理簽收／送洗頁。這次排序修改不需要更新 Apps Script。

   飯店、部門、品項須對應原本登記清單。每日不同的數量留白；固定數量可預填。是否啟用填「是」或「否」。例如：驛館／房務／浴巾／留白／條／1／是。不要把不存在於原清單的示範品項當正式設定。

2. 填入對點設定。完整程式已在 `getInventoryData` 回應加入 `sendwashSettings`，並沿用同一試算表。新分頁不存在時才建立，不改原本數量欄、收送日設定或價格資料。
3. 在 Apps Script「部署 → 管理部署 → 選擇目前 Web App → 編輯（鉛筆）→ 版本選擇新版本 → 部署」更新現有 Web App，沿用目前網址。到登記頁按原本的「更新設定」，才會將試算表的對點設定同步至 Firebase。後端未提供新欄位時，網頁保留現有設定，不會清空。
4. 在現有 Firebase 規則中評估並允許 `sendwash_records` 的讀取、建立與受限制的修改。不能將整個資料庫改成公開讀寫；新集合的權限需配合現有登入／飯店連結授權方式。已驗收來源單必須禁止飯店修改，場內驗收需有相應權限。現行網頁未登入，因此若現有規則不允許新集合，必須先完成授權設計；前端交易檢查不等於伺服器授權。
5. 用一間飯店、一個部門測試後再開其他品項。未設定對點品項時不顯示新入口，也不查詢新集合。

## 使用流程

現場實點與複點的 0 都是有效數量。計算器「清除」與「未收到：填 0」會明確填入並保存 0；退格刪到空白時顯示「尚未輸入」，不能把空白誤顯示或誤存成 0。已保存的 0 在重新載入和物流簽收單中保留，不回退至飯店送洗或先前數量。

### 洲際等「各餐廳分點、司機總簽」設定

在現有「送洗對點設定」分頁 H 欄新增標題 **餐廳**；原 A–G 欄不搬動、不新增盤點數量欄。整行欄位順序是：飯店｜部門｜品項｜預設數量｜單位｜排列順序｜是否啟用｜餐廳。

例如現有登記清單若是「洲際／餐廳／口布」及「洲際／餐廳／小毛巾」，可填：

| 飯店 | 部門 | 品項 | 預設數量 | 單位 | 排列順序 | 是否啟用 | 餐廳 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 洲際 | 餐廳 | 口布 |  | 條 |  | 是 | SEEDS(大地) |
| 洲際 | 餐廳 | 小毛巾 |  | 條 |  | 是 | SEEDS(大地) |
| 洲際 | 餐廳 | 口布 |  | 條 |  | 是 | 湛露 |
| 洲際 | 餐廳 | 小毛巾 |  | 條 |  | 是 | 湛露 |
| 洲際 | 餐廳 | 口布 |  | 條 |  | 是 | WARA |

飯店與部門**照原本登記清單的名稱填**；實際名稱若不是「餐廳」，請勿照抄示例。品項也須存在於同一部門的登記清單，不必在原登記清單複製多份餐廳品項。按試算表列順序排列餐廳與品項；預設數量通常留白，每天只填實際有送洗的品項，0 表示明確點數為 0。原本餐廳部門未指定餐廳的送洗對點列，新增分餐廳列前應先填「否」停用，避免一份數量被登記兩次；其他部門維持原樣。

此欄位需將 `hotellinen-apps-script.gs` 中更新的讀取函式部署到現有 Apps Script Web App，然後在登記頁按「更新設定」。只在試算表加 H 欄、未更新 Apps Script 的話，網頁仍看不到餐廳資訊。GitHub 網頁更新不會自動部署 Apps Script。讀取函式兼容沒有 H 欄的舊試算表，故其他飯店原本的表單不受影響。

飯店與場內的餐廳名稱呈可左右滑動的頁籤；同一送洗日各餐廳有各自來源單，同一送回日期在場內保留獨立數量和簽名。司機簽收單把同部門同品項的各餐廳**已保存的複點數量（若尚未複點，則實點數量）**加總為一筆。若尚有餐廳未點收，該餐廳不會被臆測為零；應等到全部點收完成後再請司機簽收總單。已簽署的歷史單據不會自動重算。

**洲際餐廳布品例外（2026-10-15）：**有指定「餐廳」的洲際布品不需第一步簽名。左格顯示飯店送洗數量且不可改，右格直接點開複點簽名、確認或修改數量後儲存；保存複點數量與複點簽名後才完成來源單點收，不會產生假的廠內簽名。洲際制服及其他飯店維持原本兩階段規則。

場內頁底部「今日臨時新增」會加入目前選取的餐廳，並顯示歸屬提示。司機漏填的既有品項或清單外布品都可補登；同一餐廳已有該品項時需編輯原列，不能重複新增。補登品項左格標示「未登記」，不假設飯店原本填了 0；洲際補登品項只需右格複點數量與簽名，保存後以原品項名稱加入司機總單加總。補登不修改原司機送洗單，且總單已簽收時不能再新增或修改補登數量。這次網頁調整不需重新部署 Apps Script。

- 原簽收連結仍是 `logistics.html?hotel=飯店`。新增的送洗對點按鈕放在各部門簽收按鈕下方；沒有出貨資料的部門則在日期下方顯示入口，沒有出貨資料的日子也可以填單。原有簽收按鈕保留。
- 飯店／司機進入 `sendwash.html`，送洗日期預設台灣今天，不沿用原簽收單的送回日期。填數量後送出即可，不要求簽名。空白品項不納入本次送洗單；明確填 0 則保留為數量 0。整張空白也可送出，保存「本次無送洗」紀錄，不寫入任何盤點數量；同日之後有送洗時可再更新這張來源單。
- 一飯店、一部門、一個送洗日共用一張來源單。再次送出更新同一張單；飯店和司機不會各加一筆。更新時清空的品項會從待確認來源單移除，不沿用上一版數量或預設數量。此版本不支援同一送洗日分趟建單；有多趟需更新當日總數。
- 目標日期用目前 master_template 中從试算表同步的 deliverySchedules 計算。固定收送日從隔天開始找，不使用當天；跨月、跨年以完整日期處理。未設定固定收送日的飯店沿用 index.html 現行例外（指定當日、捷中正前一日，其餘隔天），未新增其他日期規則。
- 飯店送出時再確認設定及日期沒有變更。送出的目標日期保存為來源單的一部分；後续設定變更不偷偷搬移已送出的單。若來源單需改期，必須先由管理員核對，不可自行假定新日期。
- 場內切到目標日期的登記單，看到帶入飯店數量的現場收回欄，以及等待洗滌完成的出貨複點欄。開啟待確認送洗單，實點數量預填飯店數量；不符時改實點，簽一次名儲存。
- 回廠點收交易寫入既有 count（現場收回實點）與現場 signature，並鎖定飯店來源單；來源申報數量保留在 sendwashSources。doubleCount／doubleSignature 保持空白，洗完後由複點人員在原本卡片右側另填出貨數量與簽名。尚未驗收的數量留在 sendwash_records，不寫入 inventory_records，避免被誤當成出貨或進入財務。
- 不同送洗日若依日期規則對應同一送回日，按來源單 ID 合計。重複儲存不會再加一次。每張來源單保留各品項實點及簽名。
- 若同一登記品項已有人工填寫的數量或簽名，會拒絕覆蓋，請管理員核對。回廠點收後沿用原本左右兩欄登記卡；未完成複點前，現場可重新簽名並調整收回數量。出貨複點簽名後，現場數量與簽名鎖定。

## 回廠與出貨分開確認

回廠點收與出貨複點使用兩個不同簽名。新的回廠紀錄不會自動複製現場簽名至複點簽名，也不會自動完成出貨。物流簽收單對所有品項採相同數量規則：優先採用 doubleCount，空白時帶入 count（廠內實點），不以複點簽名作為讀取條件。複點填 0 時保留 0，不回退實點數量。舊紀錄已保存的數量與簽名保留，不自動刪除或重設。這次網頁調整不用重新部署 Apps Script。
